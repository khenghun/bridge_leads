# Play v1.5 — Strict mode on prod through AWS Lambda (architecture plan)

*Drafted 2026-09-09. Status: architecture for review — nothing built. AWS account provisioning started 2026-09-10 (see *Provisioning progress* below).*

## The problem, in numbers

Strict *Expert opponents* is the play solver's one deep feature and it is
unusable on prod. Measured 2026-09-09 against the deployed app (board 7 open
room, 100 deals, one decision per request, the UI's pattern):

| Case | Laptop (8 cores / 16 threads) | Prod VPS (1 core / 2 threads) |
| --- | --- | --- |
| Plain, whole table (40 graded decisions) | 7.1 s | 37.2 s |
| Strict, declarer seat (20 decisions) | 162 s | 593 s |
| Strict, per declarer decision | 8 s | 30 s |
| Strict, slowest declarer decision | 36 s | 132 s |
| Strict, whole table (extrapolated) | 13–14 min | ~50 min |

Grades were identical (plain bit-identical; strict within the compare gate,
one decision flipping at the −0.30 line because the inner batch schedule is
thread-dependent — see *Determinism* below). The VPS (`vhp-2c-4gb`) turns out
to be **one physical core** with two hyperthreads; a 4-vCPU plan is two cores,
8 vCPUs four. DDS's batch solver scales to about four cores and then flattens
(measured on the laptop: 1→2 threads 1.8×, 2→4 1.65×, 4→16 1.1×), so the
biggest box that pays for itself is 8 vCPUs, ≈ 3× today, and it would sit
idle: the query log shows a handful of sittings a week.

The load is bursty and embarrassingly parallel at the right granularity. Pay
for compute by the second, fan it out as wide as a decision needs, and keep
the small VPS for everything else. Cost at list prices is cents per strict
table and zero inside the free tier at today's traffic. Speed is bounded by
how much of a decision we can run at once, which is what this plan is about.

## Where a strict decision spends its time

The structure decides where the remote seam can go (`engine/play/expert.py`,
`grader.py`):

1. **Layouts.** The seat's carried pool (layouts its previous decision
   accepted, still consistent) plus fresh draws for the deficit. Pure Python,
   ~1 % of the time.
2. **Suspects.** Per layout, every earlier opponent play with a real choice
   (`opponent_decisions`); in strict mode all of them are suspects, in
   default mode only those the **double-dummy trace** (`analyse_plays`, one
   DDS call per 200 layouts) says lost a trick.
3. **Judgements.** `_resolve` runs in *waves*: each wave picks one pending
   suspect per still-open layout (priority = expected rejections per second),
   dedupes by memo key, and `_judge_batch` judges them together — each
   judgement is a **sequential inner Monte-Carlo** (5-board first wave, then
   doubling, stop when the paired-difference test settles), all judgements'
   boards of an inner wave going to DDS in one call. A layout closes on its
   first rejection or when every suspect is judged consistent. Verdicts are
   memoised on `(context, index, view, holding, card)`. This is ~97 % of a
   strict decision: for a late-trick decision 100 accepted layouts × ~10
   suspects × 5–50 boards ≈ 30 000 boards.
4. **The grade.** One DDS batch of the accepted layouts (100, or 300 when
   escalated) at the graded position, ~1 s on prod.

Two facts about (3) carry the design:

- **A verdict is a pure function of its memo key.** The inner sample is
  seeded from the key; the answer does not depend on which worker computes
  it, in what order, or beside what. Only the cost moves.
- **The wave already dedupes and memoises before judging.** The outer loop
  consults the memo first, judges only misses, and writes the fresh verdicts
  back. A worker never needs the memo — it needs a list of misses and returns
  their verdicts.

So the unit of remote work is **one wave's memo misses, partitioned into
groups**, and the memo, the priority ordering, the carried pools and the
result cache all stay where they are: in the play API process on the VPS.

## Options considered

| | Seam | Round trips per decision | Keeps memo / carry-forward | Change to the engine | Speed ceiling |
| --- | --- | --- | --- | --- | --- |
| **A** | `dds_runtime` calls (every `solve_all` / `analyse_plays` batch goes remote) | ~40 (each outer wave × ~4 inner waves) | yes (all local) | one module | wave latency × 40; the inner waves' 5-board calls are latency-bound |
| **B** *(recommended)* | one wave's judgements (`_judge_batch` runs inside the worker on a group of items) | ~10 (one per outer wave) | yes | `_resolve` takes a pluggable judge backend | wave latency × ~10, each wave as wide as the number of open layouts |
| **C** | one whole decision (the analyze request itself forwarded to a Lambda running the app) | 1 | **no** — each instance has its own memo and no carried pool | none | one Lambda ≤ 6 vCPUs (~the 8-vCPU plan for that decision); ~1.5–2× more judgements |

**A** is the smallest code change and would speed up every tool, but the
inner judgement is a sequential test that draws 5 boards, looks, draws 10,
looks — remote, each look is a round trip, and a strict decision has ~40 of
them on its critical path. **C** is the smallest engineering change of all
(the frontend already sends one decision per request) but throws away the
two optimisations that made v1.4 fast, caps a decision at six vCPUs, and
turns verdicts non-deterministic across instances unless the memo moves to a
shared store. **B** sends a whole judgement to the worker — the sequential
inner loop runs locally there, exactly as today — and keeps every piece of
state on the VPS. Verdicts are bit-identical to the local path by
construction. B is the plan; A's `trace` operation rides along because the
default (non-strict) mode's dominant cost is that one big batch and it fans
out trivially.

## Architecture

```
browser --(one analyze request per decision, 1-4 in flight)--> play API (VPS, 2 vCPU)
                                                               |  grade_play -> expert_layouts -> _resolve
                                                               |    memo . priority . carried pools . result cache . query log
                                                               |    each wave: memo misses -> groups of G items
                                                               +--> Lambda bridge-play-worker x K   (judge: _judge_batch on the group)
                                                               +--> Lambda x K                      (trace: analyse_plays on a slice of layouts)
                                                               +--  local DDS for the final grade solve, and the fallback for everything
```

### The worker

- **One Lambda function, two operations**, dispatched on `op`:
  - `judge`: `{engine_sha, context, settings, inner_cap, items:[{key, layout, decision}]}` →
    `{verdicts:{key: Verdict}, boards, seconds}`. Runs today's `_judge_batch`
    unchanged on the group, with a throw-away memo (the coordinator owns the
    real one).
  - `trace`: `{engine_sha, layouts, play_prefix, strain, declarer}` →
    `{traces:[[int...]]}`. Runs `dds_runtime.analyse_plays` on the slice.
- **Same code as the API.** The worker image is a second target of the
  backend Dockerfile (`FROM backend AS worker`, adds `awslambdaric` and
  `worker/handler.py`), built by the same CI job and tagged with the same
  sha. Every request carries `engine_sha`; a mismatch is an error, which the
  client turns into a local fallback for that group and a log line — a
  half-deployed pair can be slow, never wrong.
- **Sizing.** 1 769 MB (= exactly one vCPU, the cheapest CPU-second), 60 s
  timeout, `BRIDGE_DDS_THREADS=4` for schedule parity (below). DDS at four
  threads on one vCPU was measured harmless, and 4 × 95 MB of DDS memory
  plus Python fits with room.
- **No public surface.** Invoked through the AWS SDK (`lambda:InvokeFunction`,
  SigV4) from the VPS with an IAM user that can invoke this one function and
  nothing else. No API Gateway, no function URL — nothing to rate-limit or
  authenticate ourselves.

### The client (in `app_play/`, not the engine)

- `engine/play/expert.py` gets a **judge backend** protocol with two methods,
  `judge_batch(items, **kwargs)` and `trace(layouts, plays)`, and a
  `LocalBackend` that is today's code. `_resolve` and `examine` call the
  backend instead of `_judge_batch` / `analyse_plays` directly.
  `grade_play` / `grade_position` accept `judge_backend=`; default local.
  The engine stays free of cloud imports.
- `app_play/worker_client.py` implements `LambdaBackend`: partition a wave's
  items into groups of `G` (start at 4; tune from the spike), invoke up to
  `K` Lambdas concurrently from a thread pool (boto3 `invoke`, sync), collect
  verdicts. Any group that errors, times out or reports a sha mismatch is
  judged locally, so an outage degrades to today's speed. Config by env in
  the play compose file: `BRIDGE_JUDGE_BACKEND=local|lambda`,
  `BRIDGE_WORKER_FUNCTION`, `BRIDGE_WORKER_REGION`, AWS credentials, the
  group size and concurrency cap.
- The VPS keeps: `VerdictMemo` (hits ≈ half of all judgements on the
  benchmarks, and the carried pools), the result cache, the query log, the
  final grade solve under `DDS_LOCK`.

### Determinism

- **Verdicts:** identical to local by construction — same function, same
  seeded stream, same sequential rule — *provided the inner schedule's first
  step matches*. It is `max(5, DDS threads)`, so pin the worker at 4 threads
  (= 5-board first wave, the value the regression pins were taken at; prod's
  2 threads give the same 5). Assert it in the worker's health check.
- **Grades:** bit-identical to a local run when decisions are processed one
  at a time (same layouts examined in the same order, same carried pools).
  With decisions in flight concurrently (below) the carried pool a decision
  finds may differ, so grades move within the v1.4 noise band, exactly the
  "draw-order changes are fine, within noise of the right one" gate the
  benchmarks already apply. The sequential bench stays the exactness gate.

### Concurrency across decisions (the second lever)

Fan-out shortens a decision to its wave count × wave latency. The other axis
is decisions in flight: the frontend sends a seat's decisions one at a time
today (`chunkByDecision`); with expert on it can keep 2–4 requests in flight.
The API handlers are plain `def`, so each request drives its own waves in the
threadpool; the memo is lock-protected; `pool_before` finds whatever earlier
pool exists (fewer carried layouts, never a wrong one). Both levers are
independent and cheap; concurrency is a frontend constant.

## Estimates (to be replaced by the spike's measurements)

Per-board cost on one Lambda vCPU is assumed ≈ prod's single core (both
EPYC-class; the prod strict numbers imply ~10 ms/board mid-play, ~60 ms/judgement
with the sequential stop). Warm invoke ≈ 50–150 ms from a nearby region; cold
≈ 1–3 s for a container image, paid once per burst since a wave's cold starts
overlap.

| | Prod today | Lambda, decisions sequential | Lambda, 4 decisions in flight |
| --- | --- | --- | --- |
| Strict declarer decision | 30 s | 5–10 s | — |
| Strict defender decision | 60–130 s | 10–25 s | — |
| Strict seat | ~10 min | 2–4 min | ~1 min |
| Strict whole table | ~50 min | 10–15 min | 4–6 min |
| Default (non-strict) decision | 3–8 s (trace-bound) | ~1–2 s | — |

Concurrency per wave ≈ open layouts / G ≈ 25–75 Lambdas (300-deal
escalations up to ~75); with 4 decisions in flight up to ~300. **New AWS
accounts may have a default concurrency limit of 10 — request the increase
before the spike.**

**Cost** (x86 list price, 1 vCPU-second ≈ $0.00003; ~20 % less on Graviton if
endplay's wheel builds for arm64 — not assumed):

| | CPU-seconds | Per run |
| --- | --- | --- |
| Strict declarer seat | ~700 (600 + fan-out overhead) | $0.02 |
| Strict whole table | ~3 500 | $0.10, plus ~$0.01–0.02 of invocations |
| Month at 20 strict tables + 100 plain | ~75 000 vCPU-s | $0 — inside the 400 000 GB-s free tier |
| Same at 10× today's traffic | | a few dollars |

The VPS stays on the 2-vCPU plan. The saving is the upgrade not bought; the
cost is one more moving part to deploy and watch.

## Infrastructure

- **Region:** the one nearest the VPS (Singapore → `ap-southeast-1`); measure
  RTT in the spike and record it.
- **Registry:** ECR repository `bridge-play-worker`; CI pushes the worker
  image beside the GHCR images and runs `aws lambda update-function-code`
  from the `deploy-play` job (a `deploy-worker` step, same dispatch), so the
  worker and the API change together. Rollback = redeploy the previous sha to
  both.
- **IAM:** a deploy role for GitHub Actions (OIDC, no long-lived key) scoped
  to the ECR repo and the function; an invoke-only user for the VPS whose key
  lives in `/opt/bridge_play/.env` (never in the repo; `deploy/provision.md`
  gets the step).
- **Function config** (`deploy/worker/`, applied by CI or documented for a
  one-time `aws lambda create-function`): 1 769 MB, 60 s, env
  `BRIDGE_DDS_THREADS=4`, reserved concurrency unset, provisioned
  concurrency **off** (a fixed monthly charge defeats the point; cold starts
  are one per burst).
- **Observability:** the worker returns `boards` and `seconds`; the API's
  `/api/play/debug/dds` grows a `worker` block (invocations, groups fallen
  back, mean wave latency, cold starts seen). CloudWatch's defaults cover
  errors and duration; no dashboard.
- **Not chosen:** Fargate/ECS (per-second billing but minute-scale startup
  and an always-on service to keep warm), a burst VPS (minutes to boot,
  hand-managed), API Gateway / function URLs (public surface for no gain).

## Steps

0. **Spike (½–1 day).** Hand-deploy the worker image once; from the VPS
   measure warm invoke RTT, cold start, per-board speed on a 1-vCPU Lambda,
   and the best `G`. Also confirms the account concurrency limit and that
   endplay's DDS `.so` runs under the Lambda runtime (it needs `libgomp1`,
   already in the image). Numbers replace the estimates above.
1. **The seam.** `JudgeBackend` protocol + `LocalBackend` in the engine;
   `_resolve` / `examine` through it; tests that a fake remote backend (an
   in-process worker call) reproduces the local verdicts bit-for-bit on the
   board-7 benchmark decisions.
2. **The worker.** `backend/worker/handler.py`, Dockerfile target, health
   (`engine_sha`, DDS threads, first-step size). Local test with the Lambda
   runtime interface emulator.
3. **The client.** `LambdaBackend` with grouping, concurrency, sha check,
   per-group local fallback, counters. Env config in the play compose file.
4. **CI/CD.** Build + push the worker image; `deploy-play` updates the
   function code; provisioning doc for the one-time IAM/ECR/function setup.
5. **Bench and gate.** `bench_play.py --api prod` sequential run compared
   against the laptop strict baselines (`compare_bench.py`): statuses
   identical, verdict counts identical. Then the frontend concurrency
   constant, and a second bench with it on, gated within noise.
6. **Ship.** Flag flipped on prod, `releases.ts` entry ("Expert opponents
   on the website now runs in minutes"), `checks/play.md` v1.5 section with
   the prod strict timings pinned, regression log.

## Decisions to confirm before step 1

1. **Seam B** (judgement-level, memo on the VPS) over C (whole decision per
   Lambda). C is a week less work but caps a decision at six vCPUs and loses
   the memo; B's speed ceiling is far higher and its verdicts are provably
   the local ones. *Recommended: B.*
2. **Container image, not zip**, so the worker is the backend image with a
   handler and cannot drift from the API. Cold starts a second or two
   longer than a zip. *Recommended: image.*
3. **Direct SDK invoke, no API Gateway.** *Recommended: direct.*
4. **Also remote the `trace` op** so default (non-strict) mode benefits.
   Small addition, same worker. *Recommended: yes.* The final grade solve
   stays local for now (one call, ~1 s).
5. **Frontend concurrency of 2–4 decisions** with expert on, accepting
   within-noise grade movement versus the sequential run. *Recommended: 3,
   after the sequential bench passes.*

## Non-goals

- No change to what a verdict means (tolerance, confidence, inner cap) — the
  v1.4 gate stays the accuracy contract.
- No shared memo store (DynamoDB/Redis): the memo stays in the API process
  because the wave structure never needs it remotely.
- No plain-mode or lead/contract fan-out in this version; the seam is the
  play solver's expert filter. If the lead app ever wants it, `dds_runtime`
  is the place, as option A describes.
- Nothing AI/LLM (project rule).
