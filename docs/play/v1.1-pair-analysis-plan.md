# Play Solver v1.1 — Analyze a pair, or the whole table

Play v1.0 grades **one seat** per Analyze. This release grades a **pair** or
the **whole table** in one action, because the person asking is usually one
of two partnerships at the table (sometimes both are friends) and the
question after a hand is "what did *we* do wrong" or "whose fault was it",
not "what did West do wrong".

Status: **built and verified locally 2026-09-01; not yet deployed.**
Decisions taken by the user: three actions (N/S, E/W, whole table), never a
single seat; a pair is graded as a pair. Built exactly as below, with one
addition: a pinned card the seat did not actually hold *blocks* Analyze (it is
never a matter of opinion), while HCP / length / quality exclusions only warn.

## What the user gets

Three buttons where the seat picker was:

| Action | Requests | Why that many |
| --- | --- | --- |
| **Analyze N/S** | 1 if N/S declared, else 2 | The declaring side is *one* grade — declarer's decisions already include dummy's cards (dummy makes no decisions). A defending side is two independent views: each defender saw a different hand hidden. |
| **Analyze E/W** | likewise | |
| **Analyze the whole table** | 3 | declarer + both defenders |

The labels stay concrete ("N/S — declaring 4♠", "E/W — defending"), resolved
from the contract in the loaded hand.

Results are grouped by pair, each pair a card with a summary line (role,
decisions graded, optimal / good / suboptimal, tricks lost) followed by the
per-seat decisions tables that exist today. The whole-table view adds one
**biggest swings** list at the top: every suboptimal decision from every seat,
worst first by tricks lost (by IMPs once v1.2 lands), each row jumping the
table to that moment — the port of the source's `analyze_all_players`
ranked-mistakes section, which is the only genuinely new presentation.

## How it works — frontend composition, no new endpoint

`/api/play/analyze` stays exactly as it is: one seat per request. The
frontend derives the seat list from the action and the declarer, then issues
the requests **one after another** — never concurrently: each is a DDS batch
that would only queue behind the process-global `DDS_LOCK` anyway, and
sequential lets the first seat's results render while the second solves.
A three-seat analysis therefore shows something as early as today's single
seat, and re-running the same pair is instant per seat because the service
cache is keyed per request.

Progress: one status line per seat (queued / solving / done / failed) in the
pair card. A failed seat (e.g. constraints that contradict that seat's view)
shows its error inline and does not stop the others.

Why not a `/api/play/analyze_pair` endpoint: it would be a loop around
`grade_play` returning the same three payloads, at the cost of a single long
request with no partial results, a cache key that duplicates the per-seat
entries, and a query-log row shape to invent. If a server-side composite is
ever wanted (batch review of BBO sessions), it is a ten-line route then.

## Constraints become per seat

Today the constraints editor shows the two seats hidden from the graded seat,
and the request carries only those. With up to three graded views in one
action the hidden pairs differ per request, so constraints become **what the
auction revealed about each of the four hands**, edited once per seat. Each
request sends only the entries for the seats *that request* cannot see;
entries for a visible seat are dropped for that request (the hand is known —
nothing to constrain). `toAnalyzeRequest(game, seat, constraints)` does the
filtering.

Pinned cards (`fixed_cards`) are validated as today per request — no card
claimed twice, none from a visible hand — but the play solver has an
advantage the lead tool lacks: **the real deal is known.** A constraint that
excludes the actual hand (East ≥ 12 HCP when East held 7) makes every sample
wrong by construction. The editor flags that with a one-line warning per seat
("excludes the actual East hand"), computed locally from the LIN hands; it
does not block Analyze.

## Files

- `frontend/src/apps/play/PlayApp.tsx` — action buttons, seat-list derivation
  (`seatsToGrade(action, declarer)`), the sequential runner and per-seat
  status; constraint state keyed by all four seats.
- `frontend/src/apps/play/AnalysisPanel.tsx` — pair cards, biggest-swings
  list; the existing decisions table becomes a per-seat section inside a card.
- a new `frontend/src/apps/play/analysis.ts` for the pure parts:
  `seatsToGrade`, `rankSwings(results)`, `constraintsExcludeDeal(...)` —
  unit-tested in vitest.
- `frontend/src/apps/play/changelog/releases.ts` — the v1.1 entry.
- Backend: **no change required.**

## Verification

- vitest: `seatsToGrade` for all four declarers × three actions;
  `rankSwings` ordering and ties; `constraintsExcludeDeal` on the example hand.
- Browser (run-apps skill + Playwright): the built-in example, all three
  actions; confirm the `/api/play/analyze` requests go out sequentially with
  the right `seat` and per-request `constraints`; the whole-table swings list
  jumps the table; re-running a pair is instant (cache).

## Out of scope

Point/IMP costs (v1.2); expert opponents (v1.3 — a per-request flag, so it
composes with pairs for free); any change to the grading itself.
