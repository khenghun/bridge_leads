## The port

### What the tool is

The source (`C:\kh\bridge_ai`: `api_server.py`, `solver/`, `src/`) is a
**replay-and-grade** tool, not a card-by-card player. You load a completed
hand — a BBO `.lin` file — step through the recorded play trick by trick, and
press *Analyze*: one request grades **every decision one seat made**, and each
graded decision expands to all the legal cards at that point ranked by
expected tricks. That is what gets ported, unchanged in spirit; the
card-by-card "play it from here" mode is a later feature built on the same
one-position primitive (`/api/play/position`, below).

The grading question is *"what was the best card given what this player could
see?"* — so by default the two hands the player could not see are **sampled**
(Monte-Carlo, under optional constraints) and every candidate card is
double-dummy solved on each sample. That is the same pipeline as the other two
tools, run once per decision instead of once per hand. A second method,
`double_dummy`, grades against the actual deal (one solve per decision, no
sampling) — hindsight, useful as the "what was truly best" answer.

Defects in the source that the port must **not** carry across:

- `/api/analyze` ran the whole simulation twice (a full `analyze_declarer_play`
  whose result was discarded, then `_run_enriched_analysis`).
- Doubled/redoubled contracts were dropped by the Python LIN parser.
- Defense mode wired the constraint editor to the two *known* hands.
- DDS called directly from three modules, unbatched, with no lock.
- Deal generation used the legacy rejection sampler; here it is

- BBO fetching lived in a Vite dev-server middleware (no production path) with
  a live session token hard-coded in a tracked file.

### Three decisions taken (2026-08-27)

1. **Replay & grade, as it exists.** The interactive mode is deferred; its
   primitive ships now.
2. **The API takes structured state, never a LIN string.** LIN is parsed in
   the browser only (`lib/lin.ts`); the request carries the four hands, the
   contract, and the play so far. This is the stateless contract the
   architecture section asked for, and it deletes the second LIN parser and
   the drift between the two.
3. **Tailwind is added to the frontend**, scoped to the play entry, so the
   source components port with their classes intact. The shared components
   (`ConstraintsEditor`, `DealDiagram`) keep their plain-CSS styling; the play
   page loads `index.css` first (tokens + component classes) and then its own
   Tailwind stylesheet. `tailwind.config.js` `content` lists only
   `play.html` and `src/apps/play/**`, so nothing about the lead app changes.

### Engine — `backend/engine/play/`

- `state.py` — pure replay. `replay(hands, strain, declarer, play)` validates
  each card (from the hand on turn, follows suit when able) and returns the
  position: tricks so far with winners, the current partial trick, who is on
  play, remaining cards per seat, tricks won per side. `legal_cards(position)`
  and `trick_winner(cards, leader, trump)` live here. A malformed play raises
  `ValueError` naming the play index — the API surfaces that as a 422.
- `grader.py` — the one Monte-Carlo grader, parameterised by the **view**
  seat: declarer sees declarer + dummy (defenders sampled); a defender sees
  own hand + dummy (declarer and partner sampled), except at the opening lead,
  where only the leader's hand is known — dummy is not yet faced. For a
  sampled deal the unseen hands must be consistent with the play so far:
  cards an unseen seat has already played are pinned via `fixed_cards`, and a
  seat that **showed out** of a suit has that suit's length capped at the
  cards it played in it. Those inferred constraints are ANDed with the user's
  constraints and go through `sampling.build_known_and_constraints` /
  `generate_layouts` unchanged. Each sample is then replayed to the position
  and solved in **one** `dds_runtime.solve_all` batch — one board per
  sample, since `solve_board` prices every legal card of the player on play
  at once; one lock acquisition per decision.
  `grade_position(...)` returns `{card: (mean tricks, success rate)}` for the
  side of the seat on play; `grade_play(...)` walks the play and calls it at
  every decision of the graded seat (for the declarer, that includes cards
  played from dummy). Positions with a single legal card are reported as
  `forced` and not solved. Method `double_dummy` skips sampling: one board, the
  actual deal.
- The DDS perspective trap applies at every mid-trick position: `solve_board`
  returns future tricks for the **side on play**; declarer tricks = tricks
  already won by declarer's side + (that number, or remaining − that number
  when a defender is on play). `dds_runtime` gains nothing new — a single
  position is `solve_all([...boards])`.
- Classification of a decision by `diff = actual − best` mean tricks for the
  graded side: `optimal` (|diff| < 0.1), `good` (diff ≥ −0.3), else
  `suboptimal` — the source's thresholds.

### API — `backend/app_play/` (own FastAPI app, own container)

Mirrors `app/lead/`'s `routes.py` / `schemas.py` / `service.py` shape and
reuses `app/common` (schemas, `ResultCache`, `querylog` with tool `'play'`,
`build_constraints`). Handlers are plain `def`; the query log is written
before the run; every run uses `seed=0` behind the cache.

`POST /api/play/analyze`

```
{ hands: {N,E,S,W: 'S.H.D.C'},        // the full deal, 52 distinct cards
  level, strain, declarer, vul, penalty,
  play: ['HK', 'H2', ...],              // from the opening lead, in order
  seat: 'S',                            // whose decisions to grade (dummy → 422)
  method: 'single_dummy' | 'double_dummy',
  num_deals: 5–100 (default 20; ignored for double_dummy),
  constraints: Constraints }            // unseen seats only, else 422
→ { seat, role: 'declarer' | 'defender', visible: ['S','N'],
    tricks_needed,
    decisions: [ { index, trick, position, hand, card, forced,
                   actual_tricks, best_tricks, diff, status,
                   options: [ {card, tricks, success_rate}, ... ],   // best first
                   best_cards: [...] } ],
    summary: { decisions, graded, optimal, good, suboptimal,
               total_trick_loss, avg_trick_loss },
    method, num_deals }
```

`tricks` / `actual_tricks` / `best_tricks` are for the **graded side** (13 −
declarer tricks for a defender); `success_rate` is the make rate for the
declarer and the defeat rate for a defender. `vul` and `penalty` are carried
for display and future scoring — grading is in tricks, as in the source.

`POST /api/play/position` — the same state without `seat`, `play` being the
history up to the position; grades the legal cards for whoever is on play
from that player's view. Returns `{to_play, role, options}`. This is the
interactive primitive and also the thing to `curl` when verifying locally.

`GET /api/play/health`.

### Frontend — `frontend/src/apps/play/`

- Entry `frontend/play.html` → `src/play-main.tsx`; `vite.play.config.ts`
  (same proxy, Tailwind via PostCSS, and a tiny plugin that emits the built
  page as `index.html` so the play image's nginx serves it exactly like the
  lead's); scripts `dev:play` and `build:play`. The lead entry and build are
  untouched.
- `lib/lin.ts` — the LIN parser (`md|` with 3 or 4 hands, trailing comma,
  URL-encoded strings, `sv|`, `mb|` with `d`/`r`, the play list with seat
  attribution, declarer inference: first player of the winning side to bid
  the final strain). Unit-tested.
- `PlayApp.tsx` (upload/paste screen → display screen with a sidebar: seat to
  grade, method, deal count, the shared `ConstraintsEditor` fed the two
  unseen seats), `PlayTable.tsx` (the 3×3 table with the current trick and
  played cards struck through), `PlayViewer.tsx` (the trick navigator: card
  and trick steps, keyboard), `AuctionGrid.tsx`, `AnalysisPanel.tsx`
  (decisions table, expandable options, per-card tooltips on the table).
- `api/play.ts` + `api/playTypes.ts`, mirroring the Pydantic models by hand as
  the other tools do.

### Deploy

`deploy/play/docker-compose.prod.yml` (shared backend image with the play
`command:`, `bp-*` edge aliases, `BRIDGE_DDS_THREADS: "2"`, its own `./data`
for the query log), the `bridge_play-frontend` image built on every push, a
`deploy-play` job and `play` in the `stack` dispatch choice, `/opt/bridge_play`
on the VPS. Still outside the repo: a Porkbun DNS record for the play domain
and the edge vhost in the FBO repo's `deploy/edge/` routing it to the `bp-*`
aliases — the domain name is not chosen yet.

### Deferred, deliberately

- **BBO import** (fetch hands by username). Needs a server-side fetch
  (`bbo_hands.py` has the Python for it), a session token from the
  environment, and a look at whether public hands work without one. The
  browser-side HTML→LIN parse (`bboParser.js`) ports when it comes.
- **Interactive play from a position** — the UI for it; the endpoint exists.
- **Compare two lines / trace the optimal line / grade all four seats** —
  `bridge_tools.py` has working engine bodies for these that never had a UI.
- **Scoring in points/IMPs rather than tricks** — `scoring.py` is ready for
  it; the source graded in tricks and so does this.
