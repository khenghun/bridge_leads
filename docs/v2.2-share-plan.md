# v2.2 — Results worth sharing

The design decisions behind the release, and why they are what they are.
Implementation status: **done** (2026-08-12); see `latest_updates.md` for the
work log and ROADMAP.md for the engineering summary.

## Where it came from

A competitor, <https://bridgesolver.com/>, sells essentially this app (contract
comparison + best-lead analysis over constrained Monte-Carlo deals, double-dummy
solved) at €10–100/month behind an account wall. Reviewed 2026-08-12. Their
engine choices are unremarkable next to ours — no exact-uniform sampling, no
suit quality, no pinned cards, no benchmark-relative contract ranking — but
their **presentation of a finished result is clearly better**, and their
flagship feature is the one thing our app is missing entirely: a result you can
hand to someone.

Their marketing line is "turn a bridge argument into a result". That is the use
case — a partnership disagreement, settled by a link — and it is also free
distribution: every shared link is an advert. v2.2 takes the five presentation
ideas worth taking (§1–§5). Their sixth axis — 10k–50k deal runs with saved
history and queued jobs — is deliberately **not** taken: it needs accounts,
storage, and a job queue, our VPS is 2 cores, and observed usage (11 queries in
week one) does not justify it.

Three more features (§6–§8, added 2026-08-12) come from the **production query
log** rather than the competitor: the week-one usage shows a constraint-tweaking
loop (six runs in ten minutes on one hand), a confirmation bump (re-running the
same query at a higher deal count to trust it), and returns to the same
position days apart. Each section names the pattern it answers.

Everything below is **frontend-only**. The backend, the API, and the engine do
not change. That is not an accident: the per-deal `deals` matrix both simulate
endpoints already return carries everything these features need, and `seed=0`
determinism + the result cache make recomputation a substitute for storage.

## 1. Share links

A button on the results of both tools: **Copy link**. The link encodes the
*request that produced the results* (frozen at simulate time — the form may
have drifted since) plus the view state (MP/IMP mode; benchmark on the contract
tool). Opening it restores the whole setup and **auto-runs the simulation**
(decided 2026-08-12), so the recipient lands on the result, not on a form.

Why auto-run is safe and honest:

- `seed=0` determinism means the recipient's numbers are **identical** to the
  sharer's — a recomputed result *is* the shared result, which is what lets us
  skip bridgesolver's whole accounts-and-storage apparatus.
- The `ResultCache` + dogpile protection absorb repeated opens of the same
  link; N recipients cost one simulation per cache lifetime.
- The cost of a cold open is one normal simulation — the same thing the
  recipient could do by hand.

Mechanics:

- **URL shape:** the hash already routes tabs (`#lead` / `#contract`). Extend
  it to `#lead?s=<payload>` — parse the hash as `#<tab>[?s=<blob>]`. Keeping
  the payload in the fragment (not the query string) keeps links out of nginx
  access logs and keeps `/` cacheable; the backend sees the request body on
  auto-run anyway, which is where the query log picks it up.
- **Payload:** versioned JSON `{v: 1, tool, request, view}` with empty/default
  fields stripped, then base64url. Constraint sets are ~1–2 KB of JSON, so
  links stay well under browser/messenger URL limits. No compression library —
  if payloads ever outgrow this, add one behind the version number.
- **Decode defensively.** A malformed, truncated, or future-versioned payload
  must degrade to the plain app with a visible "couldn't read this link"
  notice — never a crash, never a silently wrong prefill. The decoded request
  is *untrusted input to the form layer*, not to the API: it goes through the
  same client-side validation as typed input, and the backend's 422s remain
  the backstop.
- **On open:** decode → switch to the tool's tab → populate form state → run.
  The scenario recap (§3) doubles as the "here is what this link asked"
  banner, so a shared result explains itself.
- **Tests:** vitest round-trip (encode → decode → deep-equal), plus rejection
  cases (garbage, wrong version, missing fields).

## 2. Conclusion card

Both result views currently open with a table and let the reader infer the
answer. bridgesolver opens with the answer: *best lead ♣T, 6.28 defensive
tricks, +0.02 vs next best*. Copy that — it is the right order.

- **Lead tool:** a card above the table naming the recommended lead under the
  active scoring mode (all tied leads, as the banner already counts them), its
  metric value, its **margin over the next-best distinct lead**, and its defeat
  rate. Chips for context: contract + declarer, vulnerability, deal count,
  candidate count.
- **Contract tool:** the top candidate vs the benchmark under the active mode,
  its make %, and its mean score; the *play it from X* note when flagged.
- Recomputes instantly on mode/benchmark toggle like everything else — it reads
  the same ranking the table reads. Presentation only; no new logic beyond
  "margin vs next best", which lives beside the ranking helpers and gets a
  unit test.

## 3. Scenario recap

The result views never restate the question. Echo the frozen request back as
readable chips, bridgesolver-style: per constrained seat — HCP range, suit
lengths, shape text, quality grade, pinned cards — plus contract/vul (lead) or
seat/vul/strains (contract) and the deal count. One shared component, used by
both tools, rendered from the request snapshot the results already carry (which
is also what §1 encodes, so a shared link and its recap can never disagree).
Seats with no constraints read "any hand", as theirs do.

## 4. Equivalent-lead grouping

We solve all 13 cards and show up to 13 rows; touching cards (♦T9 from T97…)
produce adjacent rows with identical numbers, which reads as noise and pads the
table. bridgesolver groups them (imperfectly — their ♠5/♠8 rows showed
identical numbers *un*grouped; we can do it properly, from data).

- `groupEquivalentLeads()` in `lib/bridge.ts`, over the per-deal matrix:
  same-suit cards whose **per-deal trick vectors are identical across every
  simulated deal** collapse into one candidate labelled with ranks descending
  (`♦T9`). Identical vectors, not rank-adjacency, is the test — it is the
  operational meaning of "equivalent" ("no simulated deal distinguishes
  them"), it is exact over the sample, and it is what the matrix already
  proves. Cross-suit coincidences stay separate: same-suit is a display
  grouping, not a claim about the full deal space.
- The results table shows one row per group; compare-leads pickers and sample
  deal chips operate on groups, with the highest card as the representative
  for lookups. MP/IMP aggregates of grouped cards are identical by
  construction, so nothing needs re-averaging.
- Vitest: grouping on synthetic matrices (groups, singletons, near-miss vectors
  that must NOT group), label formatting.

## 5. Deal filter — browse-only

bridgesolver's result page filters the board browser by hand features: seat,
HCP range, suit length, include/exclude. That answers the natural follow-up
question — "on the deals where partner turned up with 4 spades, did it still
work?" — and every layout needed is already in `deals.records` client-side.

**Decided 2026-08-12: the filter affects only which deals are browsed.** The
ranking, the conclusion card, and every aggregate stay computed on the full
run, always. (A full re-rank over the filtered subset was considered and
declined: it silently turns a 300-deal answer into a 40-deal answer, and the
UI cost of making that honest everywhere outweighs the value.) The deal
browser shows a **"showing N of 300 deals"** badge whenever a filter is live,
in both tools.

- One criterion row, like theirs: seat (the three unseen), HCP min/max, one
  suit + length min/max, include/exclude. Client-side helpers in
  `lib/bridge.ts` (HCP and lengths parsed from the record's PBN layout),
  unit-tested.
- Applies to the sample-deal diagrams in both tools and composes with the
  existing outcome filters (compare-leads win/lose, contract makes/fails).
- **Lead-tool prerequisite:** the sample deals currently render from the
  engine's `samples` field (capped at 10 per lead, chosen server-side). A
  client-side filter over a server-chosen sample of 10 would be near-useless,
  so the sample-deal view switches its source to `deals.records` — "this lead
  defeats the contract" is computable per record from tricks — making the
  browsable set the full run, uncapped, before the filter bites. The API keeps
  `samples` (it is not our contract to break mid-release); the frontend just
  stops depending on it. The contract tool's makes/fails split already runs
  off the matrix.

## 6. "Too close to call" on the conclusion card

Added 2026-08-12 from the production query log: the visible usage pattern is a
confirmation bump — run at 300 deals, then re-run the identical query at 1000
to trust the answer. The UI offers no other way to resolve sample-size doubt.
But the per-deal matrix holds every candidate's score on every deal, so we can
*answer* the doubt instead of leaving it to a bigger re-run.

- The §2 margin ("best vs next-best distinct candidate") gains a sampling-error
  estimate, computed **pairwise**: per deal, the difference between the two
  candidates' metric contributions; margin = mean, error = `sd/√n`. The paired
  design is exactly right here — double-dummy solving is deterministic, so deal
  sampling is the *only* noise source, and pairing removes the deal-to-deal
  variance both candidates share.
- When the margin is within noise (|margin| < 2·SEM), the card says so in
  words — "too close to call at 300 deals" — instead of printing a decimal
  that looks authoritative. Alongside it, a one-click **"re-run with 1000
  deals"** button (500 on the contract tool): the same frozen request with the
  deal count raised to the cap, submitted as a normal simulation. The observed
  behaviour, turned into a guided action.
- §4's grouping runs first, so the "next-best" is the next *distinct* lead —
  never an equivalent card of the winner.
- Vitest: the paired-SEM helper on synthetic vectors, including the
  degenerate all-deals-identical case (SEM 0, never "too close").

## 7. Session run history

Same log, same sitting: six runs in ten minutes on one hand, bounds tightened
step by step. Every press of Simulate discards the previous result, so that
user compared run N to run N−1 from memory. Tabs already stay mounted to
protect results from *tab switches*; this protects them from *re-runs*.

- Keep the last ~10 completed runs per tool **in memory**: frozen request +
  response + timestamp. A compact list above the results — time, headline
  setup (contract / seat, deal count), the recommended answer — where clicking
  an entry restores that result view and repopulates the form from its frozen
  request, exactly like opening a share link minus the re-run.
- In-memory only, gone on reload, and the UI says so. Responses are hundreds
  of KB; persisting them is storage-quota trouble for no demonstrated need
  (§8 persists *setups*, which is the part users retype).
- Composes with §1: every history entry already carries the frozen
  request + view, so every previous run is shareable, not just the latest.

## 8. Restore last setup

The log also shows returns to the same territory days apart (the same hand
re-entered, the recurring 4♥-by-S theme). A reload today loses everything.

- On every simulate, write the §1 payload — same codec, same versioned shape —
  to `localStorage`, one slot per tool. On load with no share link present,
  offer an unobtrusive **"Restore last setup"** (button, not auto-apply:
  silently prefilled forms surprise, and a stale setup from last week is worse
  than an empty one). Restoring fills the form; it does not auto-run.
- Nearly free by construction: §1 builds the encode/decode and
  populate-form-from-payload machinery; this points the same codec at
  `localStorage` instead of the URL. Same defensive decode, same tests.

## Not in v2.2, deliberately

- **Accounts, saved history, server-side result storage** — §1's determinism
  argument is the whole point: a link that recomputes replaces all three at
  zero infra.
- **Bigger deal runs / queued jobs** (their paid axis) — wrong hardware, no
  demonstrated demand.
- **Re-ranking on a deal filter** — declined above, §5.
- **Opponents compete / doubling in the contract tool** — still the deferred
  headline of a future engine release (see v2.0 notes); nothing in v2.2 blocks
  or touches it.

## Order of work

1. §4 grouping (pure, small, unit-testable — and §2's "margin vs next best"
   wants distinct-group semantics, so it goes first).
2. §2 conclusion card + §3 scenario recap + §6 too-close-to-call
   (presentation over existing data; §6 is arithmetic on what §2 displays).
3. §5 deal filter (includes the lead-tool samples-from-records switch).
4. §1 share links (touches both apps' state plumbing; late because it freezes
   the request+view shape the other sections settle).
5. §8 restore-last-setup (reuses §1's codec) + §7 run history (reuses §1's
   restore-from-frozen-request path).
6. `releases.ts` v2.2 entry + ROADMAP update + Playwright pass over both tools
   (drive a share link end to end, including a malformed one).
